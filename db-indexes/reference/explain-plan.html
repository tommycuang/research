Read the work, not just the clock.

An execution plan is a tree of operations. Read its deepest indented children first, then move upward to see how each parent consumes their rows.

One node, four questions

Index Scan ... (cost=0.29..8.31 rows=1 width=40)
  (actual time=0.03..0.04 rows=1 loops=5)
FieldQuestion
costWhat arbitrary planner cost did PostgreSQL estimate? It is not milliseconds.
estimated rowsHow many rows did the planner expect this node to emit?
actual rowsHow many rows did one average execution emit?
loopsHow often did it execute? Multiply average actual rows and time by loops for totals.

Common scans

NodeMeaning
Seq ScanRead table pages sequentially. Often right for broad results or small tables.
Index ScanWalk an index and fetch matching heap rows, possibly already ordered.
Bitmap Index ScanBuild matching row locations from one or more indexes.
Bitmap Heap ScanFetch heap pages in physical order from that bitmap.

Condition or cleanup?

Index Cond limits entries reached through an index. Filter checks rows after the access step. Rows Removed by Filter reveals discarded work; multiply by loops when needed.

Buffers

shared hit means a page came from PostgreSQL's buffer cache. shared read means PostgreSQL requested it from storage. Fewer buffers often explains a stable improvement better than one timing sample.

Sorts and limits

Inspect Sort Key, Sort Method, memory, and disk. A parent LIMIT can stop requesting rows early, but only after children perform required startup work. Check how many child rows were actually produced.

Two clocks

Planning Time measures plan selection. Execution Time measures executor startup, work, and shutdown, excluding result transfer. EXPLAIN ANALYZE executes the statement and adds measurement overhead.

Evidence checklist: node tree; estimated versus actual rows; loops; index conditions and filters; rows removed; buffers; sort details; planning and execution time; returned fraction.
